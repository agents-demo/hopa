# Status

**2026-11-07.** The repository is a working PC-tethered agent plus a signed,
installed HarmonyOS app. The Python harness captures an observation, asks a
model for one action, classifies it, executes it, re-observes, verifies and
appends a hash-chained record. It has 188 agent tests (277 across the harness)
and a validated 20-task bench format. The ArkTS `apps/harmony/core` has a screen-aware
payment gate and a loop that captures observations. The HAP builds with DevEco
6.1.1 / API 24, the Local Tests pass, and the HAP is signed with the SDK's local
OpenHarmony debug kit and installed on the Pura 90 emulator (`bm install` ok,
`EntryAbility` starts, first frame drawn, six tabs render).

Device control now has two backends:

- **on-device accessibility** — extension declared, ACL granted, framework lists
  it; this emulator has no Settings page to enable it, so capture/tap stay off;
- **PC bridge** — `pc-agent bridge` over HTTP, token-authenticated, wired into
  the app and verified end to end (observe -> model -> tap -> re-observe). This
  is the path that works on this emulator.

The standalone claim is still **not** met; the toolchain, tethered, install,
UI-wiring and app-control-over-bridge claims are. The current per-capability
state is in `docs/product/coverage.md`.

## Structure (2026-11-07)

The refactor moved the whole repository to the target tree:

- `apps/harmony/{core,capabilities,entry}` — the only shippable app;
- `services/{pc-agent,brain}` — the PC-side bridge and the JVM knowledge service;
- `harness/{agent,bench}` — the reference loop and the benchmark;
- `contracts/schemas`, `tools/{scripts,checks,signing}`, and a grouped `docs/`.

Inside the app:

- `core` is OS-free: no `@kit.*` import, no capability import;
- `capabilities` are leaves: `accessibility`, `browser`, `llm`, `sandbox`,
  `system`, with no cross-imports;
- every screen is a component under `entry/pages/<area>/`;
- navigation (drawer, route host) is separate from the pages;
- `AgentService` is a 227-line composition root; `AgentRuntime` owns the loop;
- the entry page is a 396-line shell.

`tools/checks/check-structure.py --strict` (imports, barrels, file budgets) and
`tools/checks/check-links.py` run in CI. Both are clean: 0 violations,
0 size warnings, 0 broken links.

## Routing and app knowledge (2026-11-07)

The prompt now carries the app knowledge and a deterministic choice:

- `core/router/AppRouter.ets` ports the Kotlin lexical router: display name,
  aliases, bundle names and site domains are matched as whole words; the
  longest term wins; an openable target wins a tie. It runs before the loop and
  the system prompt gets one `ROUTER SUGGESTION:` line. The model is still the
  fallback, and the gate still sees every action.
- `tools/scripts/build-app-catalog.py` now derives `purpose` (the first body
  bullet) and up to four `actions` from every `APP.md`, plus site aliases and a
  site purpose. `AppCatalogPrompt` sends confirmed apps with
  `bundle - purpose | actions`, unconfirmed apps as `no verified bundle`, and
  the 21 first domains.
- A repeated `ui.launch` of the same app in one run is answered locally as
  "already launched" instead of calling `startAbility` again: HarmonyOS refuses
  background ability starts, which is why the second attempt failed on device.
- A failed launch now says why. `16000001` / `16000019` become "not installed on
  this device, or the ability name is wrong".
- The bridge has `/foreground`; `/launch` waits up to 6 s for the bundle to
  reach the front and returns it. The app retries `/observe` once on a transport
  error. When the bridge is the preferred backend it also owns `ui.launch`, so
  a launch still works while HOPA is in the background; the local launcher is
  used when no bridge is configured (for example on a phone with accessibility).
- The bridge serialises `hdc`/`uitest` calls, and the **Screens** live view
  stops polling while a run is active, so a screenshot cannot starve the
  agent's `observe`.

Verified on the emulator after the fix: with the PC bridge connected, the goal
`Open Settings` logged `route: Settings score=8`, finished with
`run: done outcomes=1`, and the only action was
`ui.launch com.huawei.hmos.settings -> ok`. `/foreground` then returned
`com.huawei.hmos.settings`. Before the fix the same request produced two launch
outcomes, the second failing because HOPA was in the background.

The full chain then ran in one request:
`Open Settings and tap Network and internet.` produced `outcomes=2` —
`ui.launch` (bridge) ok, then `ui.tap e8` ok — and the next observation was the
Settings WLAN page (25 nodes, `VirtWifi`, `Available`). That is
launch -> observe -> tap -> observe, verified on this emulator through the
bridge; the earlier failure was the duplicate launch plus `hdc` starvation from
the Screens live view.

## What works now

```bash
hopa-agent observe --json
hopa-agent run "..." --steps steps.json
hopa-agent records --path .hopa/runs.jsonl
hopa-agent verify-chain --path .hopa/runs.jsonl

cd apps/harmony
hvigorw assembleHap --no-daemon
hvigorw test -p module=core@default --no-daemon -p coverage=false
```

Sign and install with the SDK's local OpenHarmony debug kit (no Huawei account):

```powershell
.\tools\scripts\build.ps1
.\tools\scripts\sign-app.ps1 -Install
```

`tools/signing/` is gitignored; `tools/scripts/sign-app.ps1` regenerates the app key, the
certificate chain, the debug profile (with the connected device's UDID) and the
signed HAP on any machine that has the SDK.
